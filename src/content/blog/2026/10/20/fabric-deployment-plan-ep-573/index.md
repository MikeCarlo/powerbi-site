Mike Carlo and Tommy Puglia dig into the new Fabric deployment plan, argue about whether a feature without an agent is now a barrier to entry, and leave with a new word for the shop: [deplavity](https://deplavity.com).

Each item is scored on feature capability, user experience, CU or token cost, and outlook, with a note on why it earned its grade and a rating history as new rounds are released. Pipelines landed at AA+, Dataflow Gen1 rated above Dataflow Gen2, and dashboards sit at B minus. Mike's ratings lean toward data engineering and Power BI, since real-time work needs real-time sources and more capacity than he keeps running. Tommy is asking MVPs who work in real-time or data science to reach out on LinkedIn so those items get rated too.

- **[Advanced NL2SQL and advanced DAX generation in Fabric data agents (GA)](https://community.fabric.microsoft.com/blog/fbc_fabricupdatesblogs/advanced-nl2sql-and-advanced-dax-generation-in-fabric-data-agents-generally-avai/5374654)**. Instead of writing a query in one pass, the data agent now explores the schema, tests joins, and looks up real filter values before it generates SQL or DAX. Microsoft's internal benchmarks show smart-answer accuracy rising from 78.8% to 90.9% for SQL and from 89.15% to 91.86% for DAX, and the improvements roll out to the standard runtime starting November 2, with completion expected by November 10. Mike doesn't chat with data agents much. He builds with agents directly, and right now he wants to know whether an agent can build a report.

- **[Fabric Policies: granular governance at scale (preview)](https://community.fabric.microsoft.com/blog/fbc_fabricupdatesblogs/fabric-policies-granular-governance-at-scale-preview/5368144)**. Policies let admins set rules at tenant or capacity scope instead of relying only on tenant-wide switches. The preview covers item creation by capacity, selected security-sensitive workspace settings, and, coming soon, external data sharing. Mike's use case is giving a team a slice of Fabric, such as notebooks, lakehouses, semantic models, and reports, without also handing them real-time analytics. He hasn't tried it yet, but he sees it filling a gap the community has asked about for a long time.

## Main Discussion

**Topic:** Filling a gap with the Fabric deployment plan

The deployment plan was announced at the Fabric conference in Barcelona. Per the [Learn article](https://learn.microsoft.com/en-us/fabric/cicd/deployment-plan/how-to-create-deployment-plan), it's a workspace item that puts each item in its own deployment group, orders the groups by dependency, and can run actions before and after each item deploys. You attach it to a deployment in Git integration, in a deployment pipeline, or through the REST API. It's in preview, and a Fabric admin has to turn on a tenant setting before anyone can create one. Tommy calls it a process changer: if you adopt it, your team's process has to change with it.

- **Lineage gets the order right and still fails.** Tommy walks through Microsoft's [sales example](https://learn.microsoft.com/en-us/fabric/cicd/deployment-plan/deployment-plan-sample-plans). A warehouse view reads a lakehouse table that two notebooks produce. Lineage deploys the lakehouse first, but the table doesn't arrive with the item definition, so the view is created against nothing and the deployment fails. The plan runs both notebooks as post-deploy actions on the lakehouse group and makes the warehouse depend on it. To Tommy, this is Microsoft admitting that lineage covers metadata, not when data actually shows up.

- **Infrastructure, code, and data.** Mike breaks deployments into three layers: the item itself, the code inside it, and the data it needs. Deployment pipelines handle the first two. "There is no data deployment." A notebook that hydrates the data as part of the plan is the piece that has been missing since deployment pipelines came out. He also wants every environment parameterized, so the dev lakehouse GUID swaps to the next environment's lakehouse when the code moves.

- **The edge cases are real.** Mike has hit a parent pipeline that wouldn't deploy until its child pipelines existed. He has also seen a lakehouse shortcut fail in test because the upstream table didn't exist there, then revert to pointing at the development data instead of just breaking. A pre-deploy check that confirms every table exists before the shortcuts move is exactly the kind of step a plan can run.

- **A middle ground, not a replacement for Git.** If your team already lives in Git and GitHub Actions, Mike doesn't think you need a plan, because you can sequence API calls and notebook runs in actions yourself. The plan is for teams that need more control than deployment pipelines but aren't ready to do everything in GitHub or Azure DevOps actions. Tommy points out that the plan is YAML underneath, but you build it on a canvas, so you don't need GitHub Actions experience to use it.

- **Is "no agent" a barrier to entry now?** Mike admits he relies heavily on an agent whenever he builds deployment actions, and many companies still don't give their people one. For those teams, the canvas is the way in. Tommy called a timeout on the idea that anything without an agent is a barrier, so Mike offered him a raise to work without AI. Tommy said no, and when the offer flipped to 20% less pay to keep AI, he said yes. His Fabric Credit Ratings site took about a week with agents. It uses Fabric as the backend for raters, credentials, and submissions, and it publishes each released round to a static GitHub Pages front end.

- **Wait for GA, then match the plan to the team.** Mike won't recommend a preview feature for production workloads. Even after GA, he'd look at team culture first: a team that has never used Git and has only dabbled in deployment pipelines needs some pipeline experience before stepping into plans. He frames it around a release engineer: developers only touch dev, and someone else moves items between environments and makes sure the data refreshes. Tommy's summary is that deployment plans are to Fabric what deployment pipelines were to Power BI. He also flags the preview limits on the deployment plan actions page, including one plan per deployment operation and no deploying into more than one workspace in a single run.

- **Deplavity was born.** Mid-sentence, Mike tripped over his words and coined [deplavity](https://deplavity.com), and Tommy told him to trademark it before Microsoft takes it. The episode closed with a mock prescription drug ad that Mike credited to John: "Ask your capacity admin about deplavity." Today's sponsor, for the first time, was deplavity.

## Looking Forward

If deployment pipelines keep tripping over data that isn't there yet, rebuild Microsoft's sales example in a dev workspace and see whether a post-deploy notebook fixes it, then wait for GA before anything reaches production.
