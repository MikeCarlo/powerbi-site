## News & Announcements

- **[Fabric Data Warehouse integration with Fabric User Data Functions (preview)](https://community.fabric.microsoft.com/blog/fbc_fabricupdatesblogs/fabric-data-warehouse-integration-with-fabric-user-data-functions-preview/5375137)**. T-SQL external functions can map to Python functions hosted as Fabric user data functions, so SQL statements such as select, insert and update can hand work to a function and get the result back. The hosts find Microsoft's examples a little flawed, such as sending emails or PDFs, and think the bigger story is that functions can now reach data stores.

- **[Data visualization in the agentic era](https://community.fabric.microsoft.com/blog/fbc_fabricupdatesblogs/data-visualization-in-the-agentic-era/5376290)**. Microsoft describes new table visuals with sorting, resizing, embedded images, hyperlinks and data bars, and says it is rethinking how visuals get built so an agent can easily understand a visual's structure, data, interactions and style. The hosts compare the approach to Vega and Vega-Lite and ask whether it is for data agents, Fabric apps or the standard way to make Power BI reports.

## Main Discussion

**Topic:** Choosing models to build products, and thinking about repeatable, reusable dashboards, with agents in Fabric.

### Agents and the future of visuals

The hosts discuss how Power BI Desktop is mostly a semantic modeling tool for them, and that it matters less as agents become a way to build things, since Desktop cannot plug in any agent you choose. They also describe a dashboard an agent built from file data, including a panel that shows where each number came from.

### Picking a model for the job

They compare the options for Fabric workflows, Copilot, Claude, OpenAI and Grok models, and note that people using only Copilot in Fabric have limited model choice and may need an admin to enable Anthropic models. The point they keep returning to is that the most powerful model can think too much for a small task, as with a quick session name that a light model handles fine.

### Reasoning models and cheaper executors

A heavier model is useful for brainstorming and for recommendations when there are many unknowns, then a simpler model can implement a plan broken into documented steps. They mention GitHub Copilot routing a request to a more or less powerful model depending on its complexity, and the need for shared memory so context formed by one model can pass to the next.

### CLIs and MCPs

The hosts say that anything with a CLI or an MCP server is easier for agents to use, which makes the Fabric notebook toolkit and the Fabric CLI more valuable, and makes APIs and MCPs more important across Fabric workloads.

## Looking Forward

Try splitting one Fabric task between a stronger model for planning and a lighter one for execution, and keep your notes and plans in a shared place such as Notion or a GitHub repository so any model can pick them up.
